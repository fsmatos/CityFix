## Context
- Brief IV wants tickets and categories in Firestore with the offline cache. F-010 set up Firebase and the layout (decision 0010), but nothing read or wrote it.
- Anonymous users must read only `publicTickets` (CLAUDE.md, decision 0006 "Public projection contract"): Firestore rules secure whole documents, so the anonymous code path must never query `tickets` or `ticketLocations`.
- The anonymous dashboard (brief I.1.A) counts every ticket, private ones included (decision 0005 Q9), but anonymous users cannot read private tickets.
- There is no login until D-009, so F-011 needs some way to choose the audience and the creator id.
- Class material (09_Storage, T8 `AMOVStorageDemo`, 08_Coroutines_Flows_Services, P07/P08) shows one-shot `get()`, `set()`, success/failure listeners, `doc.getString(...)` mapping and `db.batch()`/`commit()`. It shows no snapshot listener.

## Decision
1. **Reads per audience (Q1).** The audience is the type of the user (sealed `User`, decision 0003), `null` meaning anonymous:
   - anonymous: `publicTickets()` only, active statuses (`whereIn("currentStatus", [OPEN, INFO_REQUESTED, IN_PROGRESS])`);
   - citizen: `participantTickets(id)` (`whereArrayContains("participantIds", id)`, full tickets) combined with `publicTickets()`; own full tickets go first and `TicketsList` keeps the first ticket with an id, so the citizen's full ticket wins over its public copy;
   - operator: `allTickets()` (every full ticket);
   - everyone: `stats()` from `stats/summary` and `activeCategories()` (`whereEqualTo("active", true)`, sorted with `Collator`).
   `publicTickets/{id}` is written only by `toPublicTicketDocument()` in `data/FirestoreMapping.kt`, which calls `toAnonymousView()` and copies the 7 keys of decision 0006's "Public projection contract" (amended 2026-11-10). All queries are single-field (no composite index); the newest-first sort runs on the client through `TicketsList(...).getAllSorted()`.
2. **Stand-in user until D-009 (Q1).** `CityFixApplication.currentUser: User? = null` (anonymous). To test another audience the person edits that line to `Citizen(DEV_CITIZEN_ID, registrationStatus = ACTIVE)` or `Operator(DEV_OPERATOR_ID)` and rebuilds. Reports use `reporterId` = `currentUser?.id ?: "dev-citizen-1"`, so anonymous reporting still works for testing. `TicketsViewModel.setUser(user)` is the seam D-009 calls on sign-in and sign-out: it cancels the old listener, clears the list (review S1, so an anonymous user never sees the previous user's full tickets) and starts the listener for the new user.
3. **Live reads as flows (Q2, beyond class).** Each read is an `addSnapshotListener` wrapped in `callbackFlow { ... awaitClose { registration.remove() } }`. The ViewModels collect them in `viewModelScope` into their own `MutableStateFlow`s (the P08 / Contacts_#3 pattern, decision 0009), so the listener is removed when the ViewModel is cleared and survives rotation. On a listener error Firestore stops that listener; we log it and do not close the flow, so the collector never throws. The flow sends nothing more and the ViewModel keeps the last list until the flow is collected again (screen reopened or user changed) (review S2).
4. **Dashboard counters in `stats/summary` (Q3).** Four numbers: `totalTickets`, `activeTickets`, `resolvedTickets`, `repairTimeSumMillis`. Every batch that changes a ticket adds `statsIncrements(before, after)` with `SetOptions.merge()`. `statsIncrements` runs the existing pure rule `TicketsList.stats()` on the ticket before and after the write and returns the difference of each counter as `FieldValue.increment` (beyond class). So the counters keep decision 0005's meaning: active = OPEN/INFO_REQUESTED/IN_PROGRESS, repair time = last RESOLVED minus `createdAt` for inactive tickets, a reopen subtracts the earlier repair, RESOLVED -> CLOSED changes nothing. A create adds 1 to total and 1 to active. The average is `repairTimeSumMillis / resolvedTickets`, computed when the document is read (`toDashboardStats()`). Both tickets passed to `statsIncrements` need a non-blank id (`TicketsList` drops blank ids).
5. **`ticketLocations` written now (Q6)**, in the create batch with `active: true`. The location is (0, 0) until F-012 adds GPS; `findNearby` already ignores (0, 0).
6. **Debug seed (Q5).** `data/DebugSeed.kt`, called from `CityFixApplication.onCreate()` only when the app is debuggable (`FLAG_DEBUGGABLE`). It reads `stats/summary` with `Source.SERVER`; if the document does not exist it writes one batch: the 4 sample categories (graffiti inactive) and the 3 sample tickets with their `ticketLocations`, `publicTickets` (all PUBLIC) and stats increments. `sample-3` (RESOLVED) gets `resolvedAt` from its RESOLVED history entry, seed only. Offline the server read fails and nothing is written. Without it nothing could resolve a ticket before D-013, so the repair-time figure would stay empty. **It must be removed before delivery** (D-015).
7. **Rules draft for `stats/{docId}` (Q7).** Read: everyone. Write: only `summary`, by an active citizen or an operator, keys only the four counters. Rules cannot check that an increment matches the ticket in the same batch, so the values are not bounded. Not deployed (decision 0012 Q5).

### Class material and beyond
- **As in class:** the single Firestore instance (`app.firestore`, F-010; the class uses `getInstance()`, ours applies the cache settings first), documents as `hashMapOf`, reading with the typed getters and a default (`getString(...) ?: ""`, `getLong`, `getBoolean`, `getGeoPoint`, as `doc.getString("name") ?: ""` in the T8 demo), `set`/`get` with success and failure listeners (the seed check), `db.batch()` + `commit()` with `addOnFailureListener` (the demo's "clear all"), and ViewModel-owned `MutableStateFlow` + `asStateFlow()` filled in `viewModelScope` (P08).
- **Beyond class, accepted at Gate 1:** `addSnapshotListener` (live updates across devices and from the offline cache; a one-shot `get()` would need a refresh), `callbackFlow`/`awaitClose` (turns the listener into a `Flow` and removes it when the collector is cancelled, the 08 slide "cancelling the collector aborts the emitter"), `combine` (the citizen's two lists), `FieldValue.increment` with `SetOptions.merge()` (counters that two devices can change at once, and that queue offline).
- **Not used on purpose:** transactions (they fail offline, decision 0010), `await()` on `commit()` (offline it completes only when the server answers, so the form would stay open), `stateIn`/`flatMapLatest` (decision 0009 keeps the ViewModel-owned `MutableStateFlow`), `toObject()` (field names differ from the model and `GeoPoint` is not `Coordinates`).
- Lists and the maps inside `statusHistory`/`attachments` have no typed getters, so those values are cast with `as?`. The person removed a guard against wrong-typed fields (a wrong type can only come from a hand edit in the console; not worth guarding in a school project), so such a document would make the typed getter throw inside the listener and crash the app. Missing fields and unknown enum names do not throw: they read as the model default.

### Rejected
- **Q1:** a debug "View as" menu (strings and UI for a temporary tool); waiting for D-009 (blocks F-012/F-013).
- **Q2:** callback functions returning a small `Subscription` handle, closer to `addOnSuccessListener`, with the ViewModel cancelling the handles in `onCleared()` and `setUser`: more bookkeeping by hand.
- **Q3:** (b) statistics over `publicTickets` only (leaves out private tickets, against decision 0005 Q9); (c) an operator's device recomputing `stats/summary` on each snapshot (stale when no operator app is open, and none exists before D-013); (d) Firestore `count()`/`average()` aggregations (server only, no offline, and anonymous users cannot query `tickets` under the drafted rules).
- **Q5:** categories only (no resolved ticket, empty repair time); a debug button (strings and UI); typing the data in the console.
- **Q6:** writing `ticketLocations` only in F-012 (tickets made before then would have none).
- Firebase Anonymous Auth for anonymous users (brief I.1, decision 0010).

## Consequences
- A report on one device shows on another without a refresh; this device shows it at once from the local cache, before the server has it.
- `reportTicket` returns once the batch is queued. A write the server later refuses (possible only once rules are deployed, or after the test mode ends on 2026-12-10) is only logged, not shown to the user.
- After a listener error the screen keeps the last list with no live updates until the flow is collected again.
- With an empty cache and no network at first install, lists, dashboard and categories are empty and the form cannot be submitted (no category). Brief IV's offline promise applies after the first sync.
- **Counters can drift** if a write path forgets `statsIncrements`. Every batch that changes a ticket (D-013, F-014) must add it. Repair: recompute the four counters by hand from `tickets/` in the console. Deleting `stats/summary` to let the seed run again is not a repair: the seed would set the counters to the 3 samples only.
- `toTicket()` ignores the Firestore `resolvedAt`; the model's `Ticket.resolvedAt()` uses the RESOLVED history entry. D-013/F-014 decide whether to map it (decision 0010 says clients compute the window from it).
- Until F-013, `publicTickets.thumbnails` is empty and `storagePath` holds a local path, so other devices show the card placeholder. **Done by F-013 (2026-11-14, [decision 0017](0017-media-preparation-and-uploads.md)):** once uploaded, entries hold download URLs and the worker adds the public thumbnails; other devices still see the placeholder while an entry is PENDING.
- Test data with stand-in ids (`dev-citizen-1`, `citizen-1`, `citizen-2`) is in the shared test database; D-015 decides whether to clean it.
- `currentUser`, `reporterId` and `DebugSeed` are temporary: D-009 replaces the first two, D-015 removes the seed.
