## Context
- **Brief I.3.E:** the operator has an operations panel with every report, its coordinates, the author's contacts and the full history with photos and videos, and controls the lifecycle: status changes with timestamps, requesting information, recording the start of work, and uploading a photo/video of the finished work. **Brief II.2-II.5:** the transition order and the locked CLOSED state (section II not checked in the PDF, overview "Brief status").
- **Decision 0011 (D-008):** `allowedTransitions(by, now)` and `transition(to, by, now, justification, proof)` are the only way to change status; RESOLVED needs fresh proof, stamped `phase = RESOLUTION`. No `addResolutionProof` is needed.
- **Decision 0018 (F-014):** Francisco's private `commitStatusChange(before, after, message?)` writes one batch (ticket status fields, `publicTickets` status mirror for PUBLIC, `ticketLocations.active = isActive`, `stats/summary` increments, optional message). `askForClarification(ticket, by, question)` already does the INFO_REQUESTED move plus a message in that batch, for any `User`. `detailAudience` already returns OPERATOR for operators.
- **Decision 0017 (F-013):** `AttachmentUploader.prepare` + one `enqueue(documentPath, ticketId, addPublicThumbnail)`; the worker uploads only entries whose file is on this device.
- **The operator's shared list is already complete:** `TicketsViewModel.setUser(Operator)` listens to `allTickets()` (F-011), so the task file's `operatorTickets()` is not needed.
- **Rules drafted, not deployed** (decision 0012 Q5, amended 2026-11-13): the test-mode database accepts any write until 2026-12-10.

## Decision
- **Panel source and filter (Q5).** `OperatorPanelScreen` reads the shared `TicketsViewModel.tickets` (no second listener). The filter is pure: `model/TicketFilter.kt`, `TicketFilter(status, categoryId, newestFirst)` and `List<Ticket>.filteredFor(filter, now)`, which compares the **effective** status (an expired RESOLVED ticket is under Closed, with no write), the category by id, and orders by `createdAt` with the id as tie-break. `OperatorPanelViewModel(categories)` holds only the filter and the category list from `CategoriesRepository.allCategories()` (inactive ones included, so old tickets can be found).
- **Operator detail as a branch, not a route (Q1).** In `composable<TicketDetailRoute>`, `user is Operator` renders `OperatorTicketScreen` with an entry-scoped `OperatorTicketViewModel(tickets, users, attachmentStorage, ticketId, operator)`; participants keep F-014's view, everyone else `ShowScreen(PUBLIC)`. One route, one view per role (decision 0007's idea). Contacts (`observeUser` of other users, `PersonContact`) and history names exist only inside this branch.
- **Repository methods in Francisco's `TicketsRepository` (Q2).** `startWork(ticket, by, note?)` and `suspend resolveTicket(ticket, by, proof, note?)`, both over `commitStatusChange`, which gains one optional `newAttachments: List<Attachment> = emptyList()`. Request information reuses `askForClarification` unchanged (KDoc line only). `Attachment.toDocument()` becomes `internal`.
- **Resolve with proof (Q11).** 1 to 3 photos or videos (gallery photo/video or camera photo; no video recording), optional note. `resolveTicket` on `Dispatchers.IO`: dry run of `transition(RESOLVED)` with the raw draft (rejected -> nothing prepared); `prepare` each proof; stop if none is PENDING (originals kept, the draft survives); real transition with the prepared proof; one batch with the new entries appended by `FieldValue.arrayUnion`; after `commit()` (not awaited), one `enqueue("tickets/<id>", id, false)`. `false`: proof thumbnails never go to `publicTickets.thumbnails` (decision 0010, REPORT only).
- **Start work with a confirmation (Q6):** a dialog with an optional note (stored as the justification), because there is no undo.
- **The thread lives in the operator ViewModel (Q7):** the same three functions as `TicketDetailViewModel`, so one screen has one ViewModel.
- **"By <name>" for operators only (Q3, Q13):** an additive `responsibleNames: Map<String, String> = emptyMap()` on `ShowScreen`, filled only by the operator detail; citizens see dates and "Municipality" in the thread, never operator names.
- **"Resolution proof" label on `MediaTile` (Q4)** for `phase == RESOLUTION`, every audience (not personal data; D-008 review N2).
- **No INFO_REQUESTED -> OPEN (Q8):** the operator's only move out of INFO_REQUESTED stays Start work (brief II order); the operator answers in the thread.
- **No rules edit, no deploy, no `resolvedAt` (Q9).** Times come from the history entry (decision 0018 Q7).
- **Actions come only from `allowedTransitions(operator, now)`:** INFO_REQUESTED -> "Request information", IN_PROGRESS -> "Start work", RESOLVED -> "Resolve". A locked ticket shows no action and no message input. The Resolve section shows only while Resolve is offered or during this operator's own save (review S1), and a dialog only while its target is offered (review N1).
- **D-014 hook only:** `Ticket.needsOperatorGeofence(now)` in `model/TicketLifecycle.kt` (effectively IN_PROGRESS and a real location). No geofence code.
- **`PlaceholderScreen` kept (Q10 not applied):** `PendingValidationScreen` still calls it.

### Rejected
- **A separate operator tickets repository with its own batch** (the D-012 pattern): it would duplicate the batch and counters logic of `commitStatusChange`.
- **A generic `changeStatus(to)`:** a caller could move to RESOLVED without proof or to INFO_REQUESTED without the message; explicit methods mirror F-014's `reopenTicket` / `askForClarification`.
- **`addResolutionProof` as a separate write:** the proof and the RESOLVED entry belong in one batch (D-008).
- **A second `allTickets()` listener for the panel:** the shared list already has it.
- **A new `OperatorTicketRoute`:** two routes for one ticket, and F-014's view would stay reachable for operators from the public list.
- **Rewriting the whole `attachments` array on resolve:** it could overwrite a concurrent `UploadWorker` update of the creator's entries.
- **`requestInformation(...)` alias:** more surface for the same batch.

## Consequences
- **Operator-only actions and contact visibility are enforced by the app only (R4).** `RequireAccess(OPERATOR)` on the panel, the `user is Operator` branch, the ViewModel created inside it and the repository re-running `transition()`. Against the test-mode database any client with the project config could write a status.
- **The draft rules would refuse the resolve batch (Q9, not fixed).** It writes no `resolvedAt`, which the drafts check (`resolvedAtIsServerTime`); F-014's reopen has the same mismatch. Changing the rules (accept a missing `resolvedAt`, or write `FieldValue.serverTimestamp()` on resolve) needs Diogo's explicit OK and Francisco's agreement. Not deployed, so nothing fails today.
- **Concurrent status changes are last-write-wins.** No transaction (transactions fail offline, brief IV) and no precondition on `currentStatus`; two operators acting at once can each append an entry, and the later batch's `statusHistory` replaces the earlier one. This supersedes decision 0011's expectation of "a transaction or a precondition".
- **F-013's attachments race is unchanged** (two workers' get-then-update); the resolve batch itself does not add to it (`arrayUnion`).
- **The proof draft is lost on process death (review N5).** It lives in the ViewModel, not in `SavedStateHandle`, so its local copies stay on the device as orphans. Rotation keeps it.
- **`onCleared` deletes the draft's files on the main thread (review N2).** `viewModelScope` is already cancelled there and the app has no application scope; at most 3 local deletes, as `ReportViewModel`. Documented in the code.
- **Leaving during preparation** cancels `viewModelScope`: nothing is written, and files already prepared may be orphaned (rare).
- **D-014 builds on `needsOperatorGeofence`;** INFO_REQUESTED pauses it by construction. "Work started" notifications are F-016's (a transition to IN_PROGRESS by an operator).
- **Not done:** the panel map (slice 8) and the joiners' `reports/{uid}` in the operator detail (slice 9, F-012 handover still open).
- **Not verified (no device check run yet, D1-D11):** the panel with another citizen's PRIVATE ticket and the "Private" label; status chips (expired RESOLVED under Closed), category filter, sort, rotation; the detail's map, history, media and contacts, and "Contact not available" offline; a citizen and an anonymous user seeing no contacts or names; buttons per status; Request information (blank error, entry + message, citizen live on a second device); Start work ("By <name>", `needsOperatorGeofence` true); Resolve disabled with no proof and the console fields after it (stats, `ticketLocations.active` false, no public thumbnail); the offline resolve with the app closed; closed / expired tickets read-only with the CLOSED entry written once; rotation with each dialog and the resolve section; landscape.
