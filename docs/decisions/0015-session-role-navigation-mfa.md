## Decision
- **One sealed `Session` in an activity-scoped `SessionViewModel` above the `NavHost` (Q3).** `viewmodel/Session.kt`: `Loading`, `Anonymous`, `NeedsEmailVerification(email)`, `NeedsSecondFactor(email)`, `ProfileMissing`, `ProfileUnavailable`, `SignedIn(user)`. Order of checks: no account, e-mail not verified, no factor, profile missing or unavailable, signed in. Pure helpers in the same file: `enum class AccessRole { LOADING, ANONYMOUS, SETUP, ACCOUNT_PROBLEM, PENDING_CITIZEN, CITIZEN, OPERATOR }` (one value per home screen), `Session.accessRole`, `Session.canReport` (active citizen only) and `Session.isSignedIn`. The ViewModel is created with `SessionViewModelFactory` like `TicketsViewModel`, so every destination shares it and it survives rotation.
- **Auth and profile kept apart, combined in the ViewModel** (deviation from the task's `currentUser: Flow<User?>`). `AuthRepository.account: StateFlow<AuthAccount?>` (uid, e-mail, verified, has a factor) and `UsersRepository.observeUser(uid): Flow<UserProfile>` (`Found`, `Missing`, `Unavailable`). `SessionViewModel` runs `combine(account, retries).flatMapLatest { ... }`: logging out or changing account cancels the old `users/{uid}` listener; Retry bumps a counter and restarts it.
- **MFA mandatory for both roles, enrolled in D-009 (Q1, Q8).** An account with no factor cannot reach any role feature. Account setup (`AccountSetupRoute`) takes it through: verify the e-mail (the link, then "I have verified", which runs `reload()` + `getIdToken(true)`), then enter a +351 number, then the SMS code, then `enroll`. The setup step comes from `AuthRepository.account`, the same source the session uses. The phone digits, the verification id and the "e-mail sent" flag are in `SavedStateHandle`.
  - The server-side check (`request.auth.token.firebase.sign_in_second_factor != null` in `isActiveCitizen()` / `isOperator()`) was planned for the rules-deploy step, with Diogo's OK (Gate Q1 sub-question). Since decision 0012 Q5 (2026-11-13) there is no deploy, so **MFA is enforced only in the app**. D-009 does not edit the rule files; adding the line to the drafts, as documentation of the server design, is a choice for both authors (handover in the overview).
- **Pending citizens may log in (Q2).** Their home is `PendingValidationScreen` ("waiting for validation by the council") with a button to the public dashboard. They have the anonymous features only: no report, no My tickets; Profile (D-011) is allowed. Activation switches them live to the citizen home through the `users/{uid}` listener.
- **Guarding in three layers (Q4).** (1) Hidden entry points: the add button only when `canReport`; the overflow menu from `menuItemsFor(role)`; Log in only for ANONYMOUS, Log out for every signed-in state. (2) `RequireAccess(role, allowed, onDenied)` wraps the report route and every role destination; when the role is not allowed it draws nothing and navigates home. (3) One redirect `LaunchedEffect(role)` in `CityFixApp` navigates to `homeFor(role)` with `popUpTo(graph.id) { inclusive = true }`. The Firestore rules would be the real enforcement, but they stay undeployed drafts (decision 0012 Q5), so in this delivery the guards and the repositories' queries are the only enforcement.
- **Redirect rule, including cold start (review B1).** The last role handled is kept in `rememberSaveable` (`handledRole`):
  - `role == handledRole`: nothing happens (rotation; the `SessionViewModel` keeps the role).
  - `handledRole != null` and the role changed (login, logout, activation, process recreation with a changed role): go home.
  - `handledRole == null` (a **fresh** cold start; nothing restored): go home **unless** `homeFor(role)` is the dashboard, which is the start destination already. So an operator, a setup user, a pending citizen and an account-problem user land on their home after a cold start with a stored session.
  - The effect sits inside the `Scaffold` content **after** `NavHost(...)`, so the graph is set when `goHome()` runs, and it is never composed while `Loading`.
  - Process recreation restores `handledRole`, so the restored back stack is kept.
  - The 01-coding-plan (slice 3) said "the first value is only recorded"; that was the bug the review found (B1), fixed in `8524ea1`.
- **Redirect hold for registration (D-010, 2026-11-14, [decision 0016](0016-registration.md)).** Sign-up signs the new user in at once, so the redirect is now `LaunchedEffect(role, holdRedirect)`, and it does nothing while `holdRedirect` (`rememberSaveable` in `CityFixApp`) is true. The Register screen holds it while it registers, and after a failure until the deleted account reaches the session. Register counts as an auth screen (`onAuthScreen`): no 10 km gate, no menu, no account action. The Up arrow is hidden while the hold is on.
- **Loading gate.** While `Session.Loading`, `CityFixApp` shows a labelled progress indicator instead of the `NavHost`, so an operator never sees the dashboard flash. `startDestination` stays `DashboardRoute`.
- **Offline from the Firebase caches only (Q5).** Firebase Auth persists the user; `users/{uid}` comes from the persistent Firestore cache (F-010). No copy in DataStore or SharedPreferences. A non-existent document that comes **from the cache** is `Unavailable` (offline, a never-read profile looks missing), only a server answer without it is `Missing`.
- **Login, Forgot password and Account setup are routes; the SMS code is a step of `LoginRoute` (Q6).** The `MultiFactorResolver` is not serialisable, so it cannot go into a route. It is wrapped in an opaque `SecondFactorChallenge` (`data/`) and kept in a private field of the route-scoped `LoginViewModel`, never in `UiState` or saved state; after process death the login returns to the credentials step with the e-mail kept. `ForgotPasswordRoute(email)` carries only the typed e-mail. `MfaCodeContent` (`MfaScreen.kt`) is the stateless code entry shared by login and setup.
- **Nobody gets the expand toggle (Q7, deviation from the plan).** The plan recommended `canExpandCards` for operators. Diogo decided that it stays `false` for every session. At Gate 1 `tickets` was the projected public list; since F-011 and the session wiring an active citizen's list holds their own plus the public tickets and an operator's holds all, but the cards and the detail still render only the public fields for every role, so an expanded card would add only the date; brief I.1.B lists category, situation and thumbnail, and I.2.D gives citizens the anonymous features. The operator's full view is D-013's panel (I.3.E), not this list. The D-007 flag and its `canExpandCards && isExpanded` stay in `CityFixApp` for a later decision; there is no `Session.canExpandCards`.
- **Console-seeded test accounts (Q9).** Auth users with real inboxes plus hand-typed `users/{uid}` documents; no seeding code.
- **The `Activity` goes through the ViewModel call, never stored.** The stateful screen reads `LocalActivity.current` and passes it to `sendCode(activity)`, which passes it to `PhoneAuthOptions.setActivity` (needed for the reCAPTCHA fallback). It is held by the pending coroutine for at most 60 s.
- **`requireSmsValidation(true)`.** The code is always typed; `onVerificationCompleted` (instant verification or auto-retrieval) is ignored, so there is one completion path. The code field has `ContentType.SmsOtpCode` semantics so the autofill service can offer the code. `CodeSendResult.Sent` has no auto-retrieved code (deviation from the coding plan: with a suspend send that resumes on `onCodeSent`, a later completion has nowhere to go).
- **Callbacks as a suspend call.** `verifyPhoneNumber` is wrapped in `suspendCancellableCoroutine` inside `withTimeoutOrNull(60 s)`; a timeout returns `CODE_NOT_SENT` and the screen offers Resend.
- **First phone hint only (Q13).** Accounts have one factor; enrolling a second one is not offered.
- **The session drives the tickets (2026-11-14, `46ee41f`).** `Session.ticketsUser` (`viewmodel/Session.kt`) is the profile for `AccessRole.CITIZEN` (active) and `OPERATOR`, and `null` for every other state (anonymous, loading, setup, pending citizen, account problem), which gets the public tickets only. `CityFixApp` creates `TicketsViewModel` with `null` and calls `setUser(ticketsUser)` from `LaunchedEffect(ticketsUser)`. `TicketsViewModel.setUser` (written by F-011; D-009's only change there) returns early when the role and id equal the last applied ones (`appliedUserKey`, for example `"citizen:<id>"`), so rotation, process-death re-application and profile-only changes (for example `fcmTokens`) do not restart the listener or blank the list.
- **The report's creator is the signed-in citizen.** `ReportViewModelFactory` receives `session.ticketsUser?.id` inside `RequireAccess(CITIZEN)`, which is the Auth uid (the `users/{uid}` document id) that the draft `tickets` create rule compares with `creatorId`. The F-011 stand-ins (`currentUser`, `reporterId`, `DEV_CITIZEN_ID`, `DEV_OPERATOR_ID`) are removed from `CityFixApplication`.
- **10 km gate only for the anonymous user (brief I.1).** `showGate = role == ANONYMOUS && !onAuthScreen && status != INSIDE`: never while `Loading`, never for a state with an account, and not on Login / Forgot password / Account setup, which the gate's **Log in** opens (`onLoginClick` navigates to `LoginRoute`). The gate is drawn in a `Box` **over** the `Scaffold`, inside an opaque M3 `Surface` that takes the touches; while gated, the Scaffold gets `clearAndSetSemantics {}` (TalkBack) and the top bar gets `canNavigateBack = false` and `accountAction = NONE` (review R3-N2; add and menu are already off for ANONYMOUS). Because the `NavHost` stays composed behind the gate, its graph is set when Log in navigates. After login the role is not ANONYMOUS, so the gate does not return; Back from Login brings it back.
  - **Pending citizens are not gated (review R3-N3).** A `PENDING_CITIZEN` is authenticated, so brief I.1's literal reading does not limit them, and "Browse public issues" works anywhere. Consequence: once D-010 exists, registering (password + MFA) lifts the 10 km limit before an operator validates the account. Diogo may choose the stricter reading later by adding `PENDING_CITIZEN` to `showGate`'s condition (one line). SETUP and ACCOUNT_PROBLEM have no route to the public screens, so they do not matter.
- **Log out clears the tickets first (review R3-S1, `f141ae4`).** One `logOut` helper in `CityFixApp` calls `ticketsViewModel.setUser(null)` and then `sessionViewModel.signOut()`; the top bar (icon and menu entry), Account setup and Account problem all use it. So the frame after Log out never shows the previous user's own or operator-only tickets; the later `LaunchedEffect(ticketsUser)` with `null` has the same key and returns early.
- **E-mail sync and re-authentication (D-011, 2026-11-16, [decision 0019](0019-profile-editing.md)).** In the signed-in branch, `SessionViewModel` compares the first `Found` snapshot with the Auth e-mail and, when they differ (ignoring case), calls `users.syncEmail(uid, email)` (one field, not awaited). Later snapshots in the same branch never write, so a stale second device cannot start a write loop. The check runs again when the branch restarts: a sign-in, a reload that changes the account, `retry()`, or a resubscription after more than 5 s in the background (`WhileSubscribed(5_000)`, review R2-N1), so a stale device can write the old e-mail once per return until its token is refused (accepted). `resolveSecondFactor` also completes the re-authentication started by `AuthRepository.reauthenticate(password)`; on the emulator the session stayed `SignedIn` through it (R1).
- **Errors in one mapping.** `FirebaseAuthRepository.toAuthError()` maps Firebase exceptions to `AuthError`, and `viewmodel/AuthErrorMessages.kt` maps `AuthError` to string resources for the three screens. Wrong e-mail and wrong password give one message (e-mail enumeration protection); the reset confirmation is the same for unknown e-mails. Every `catch (e: Exception)` is preceded by a rethrow of `CancellationException` (review S3).

### Rejected
- **Per-role navigation graphs:** navigating to a route not in the current graph throws `IllegalArgumentException`, a crash path.
- **A `startDestination` that follows the session:** changing it resets the graph.
- **A `CompositionLocal` session:** a hidden dependency; decision 0007 rejected the same for the detail audience.
- **A DataStore or SharedPreferences role cache:** a second source of truth next to the Firebase caches.
- **TOTP:** needs an authenticator app at the defence (decision 0012).
- **Optional MFA:** against I.2.B / I.3.B.
- **An own e-mail one-time code:** needs a server.
- **Debug seeding code:** it would write `role: OPERATOR` from the client, which the draft rules forbid without a verified domain e-mail, and it is code to defend for no feature.
- **`setAppVerificationDisabledForTesting`:** documented for phone sign-in, not for MFA. R2 (a reCAPTCHA page on the emulator) has not been observed yet; if it forces this flag, it would be debug-only, need Diogo's OK, and be recorded as an amendment here.
- **`canExpandCards` for operators** (the plan's Q7 recommendation): an operator's expanded card would still show only the date until D-013 gives operators an unprojected source.
- **The gate as an early `return` before the `Scaffold`** (the merge's first version): with no `NavHost` composed, the gate's Log in had no graph to navigate in.
- **Gating every state but CITIZEN/OPERATOR** (pending citizens included): stricter than brief I.1's wording; left open for Diogo (R3-N3).
- **Reading `FirebaseAuth` in composables** (`.claude/rules/kotlin.md`); **Hilt** (decision 0009).

## Consequences
- **Gap after the second factor (review N7).** Between `resolveSignIn` and the first `users/{uid}` snapshot, the account is set but the profile listener has not emitted yet. `flatMapLatest` + `stateIn` keep the **last** value, so the session is still `Anonymous` for that moment, not `Loading`. Nothing wrong is visible: Login stays busy after success until the redirect leaves the screen, and Log in is hidden on the auth screens. The same kind of gap follows `enroll()` on the setup screen (the session stays `NeedsSecondFactor` until the profile arrives). The states before the profile (`NeedsEmailVerification`, `NeedsSecondFactor`) are `flowOf` values and have no gap. Code that reacts to the session (for example F-016 storing an FCM token) must wait for `SignedIn`, not for "not Anonymous".
- **Rotation during the code send (R3).** The Firebase callbacks are bound to the activity and detached when it stops, so a rotation during the send can lose `onCodeSent`. The 60 s timeout turns that into "Could not send the code" with Resend. Not observed on a device yet. On Login, Back is enabled during a send (review N2; a stale answer is dropped by `challenge !== current`); on setup, Back is disabled while busy (R2-N2, kept on purpose).
- **Login needs the network**; a cached session does not.
- **One factor per user:** a lost phone means a reset by an operator or in the console. There is no self-service recovery.
- **MFA is enforced only in the app.** The rules stay undeployed drafts (decision 0012 Q5), so there is no server check of `sign_in_second_factor` (and none of the other rules); a client that skips the app's setup gate could use the API with only a password. The database is in test mode until 2026-12-10. State this at the defence.
- **Involuntary sign-out keeps a one-frame gap (review R3-S1).** The `logOut` helper covers every Log out the user presses. If Firebase signs the user out by itself (token revoked, account deleted or disabled), the session becomes `Anonymous` first and `LaunchedEffect(ticketsUser)` clears the list one frame later, so for one frame the List or Detail screen can still draw the previous user's tickets (anonymous-style cards, public fields only) before the redirect. Accepted: rare, and only the same device's previous user could see it.
- **Pending citizens outside 10 km** use the public screens (R3-N3, above).
- **System Back behind the gate.** While the gate shows, system Back still acts on the `NavHost` behind it; this only matters if the gate appears mid-session (anonymous user moving out of the 10 km area). Accepted.
- **Verification e-mail per entry (review N4).** The setup screen sends the verification e-mail once per back-stack entry, not once per account; each login or cold start of an unverified account sends another one and may hit `TOO_MANY_REQUESTS`. The intro text no longer claims the e-mail was sent. Accepted for the prototype.
- **Placeholders.** `MyTicketsRoute` (F-014), `ProfileRoute` (D-011), `OperatorPanelRoute` (D-013), `ApprovalsRoute` and `CategoriesRoute` (D-012) show a shared `PlaceholderScreen`; the later tasks replace the content inside their `composable<>`, keeping the `RequireAccess` wrapper.
- **Detail audience unchanged.** Every session gets `DetailAudience.PUBLIC` at the call site, so the detail renders only public fields even when the ticket comes from a citizen's own or the operator's full list; mapping role + creator/follower to `REGISTERED` / `OPERATOR` is F-014 / D-013 (decision 0007).
- **Not verified on a device.** The acceptance checks, the console steps, the `errorCode` strings for wrong and expired codes (`ERROR_INVALID_VERIFICATION_CODE`, `ERROR_SESSION_EXPIRED`, taken from the docs), R2 and R3 are open (list in `docs/work/D-009-auth-mfa-role-navigation/review.md`).
