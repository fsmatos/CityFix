# 0014: Location, anonymous gate, 10 m grouping and map

Status: accepted (F-012, Gate 1 on 2026-11-14 with the defaults Q1-Q9, Q5 as updated before the Gate, no try/catch around the grouping query; changed by the person after Gate 1 on 2026-11-14 to follow the class practical Contacts_#3 / P10: Google Maps Compose, the Maps key in the manifest, the permission request at app start; review fixes S1, N2-N4 on 2026-11-14). Amends [decision 0002](0002-grouped-reports-single-ticket.md) (Q5), [decision 0010](0010-firestore-schema.md) (`ticketLocations.active`, `reports/{uid}` attachments) and [decision 0012](0012-firebase-plan-notifications-close-maps.md) (Q6, maps). The number 0014 was free on `dev/Francisco` when this was written (confirm with Diogo that `dev/Diogo` has not used it).

## Context
- Brief I.1: anonymous citizens may use the app only within 10 km of Praça da República. Brief I.1.C: the anonymous detail shows the place on a "mapa com zoom afastado". Brief I.2 Obs.: a report with the same category and situation within about 10 m of an existing one is grouped, so several citizens follow one problem (Option A, decision 0002).
- Until F-012 reports had no location (0, 0), so the grouping could never match, and `CoarseLocationMap` was a static placeholder (F-005 Gate 1 Q7).
- Class material: Contacts_#3 / P10 (updated 2026-11-13) uses `play-services-location` 21.3.0 (`FusedLocationProviderClient`), requests FINE and COARSE in `MainActivity` with `LaunchedEffect(Unit)` + `rememberLauncherForActivityResult(RequestMultiplePermissions())`, shows a `GoogleMap` with a `Marker` at zoom 15 (`maps-compose` 6.1.0, key in the manifest `com.google.android.geo.API_KEY` meta-data) and receives continuous updates in a `ProximityService`.
- Firestore has no geo query. Citizens cannot read other people's `tickets`, so the grouping reads `ticketLocations` (decision 0010).
- The brief says nothing about scope (PUBLIC/PRIVATE) or about the joining reporter's photos in a grouped report.

## Decision
1. **Location.** `data/LocationRepository` (one per app, `CityFixApplication.locationRepository`) wraps the `FusedLocationProviderClient` and has one function, `suspend fun currentLocation(): Coordinates?`: it checks the permission itself and calls `getCurrentLocation(PRIORITY_HIGH_ACCURACY, null).await()`. `null` means no permission or no fix (location off). One fix, not continuous updates: a report and the gate need one position. D-014 adds updates in the same class.
2. **Permission at app start, as in class.** `MainActivity` requests FINE and COARSE together at start (`LaunchedEffect(Unit)` + `RequestMultiplePermissions`), and the answer goes to the gate. There is no explanation panel before the system dialog. A denial shows a clear message with "Try again" (asks again) and "Open settings" (needed after "don't ask again", when Android shows no dialog). This departs from `.claude/rules/kotlin.md` ("at the point of use with a rationale"), by the person's choice.
3. **The 10 km gate (Q1-Q3).** Centre and radius are code constants in `model/AnonymousArea.kt` (`PRACA_REPUBLICA = (40.2100, -8.4190)`, `ANONYMOUS_RADIUS_METERS = 10_000.0`) with the pure rule `isInsideAnonymousArea` over `haversineMeters`; (0, 0) is outside. `LocationGateViewModel` has `GateStatus { CHECKING, DENIED, NO_FIX, OUTSIDE, INSIDE }`. `MainActivity` shows `LocationGateScreen` instead of the app while `app.currentUser == null && status != INSIDE` (early `return` before the `Scaffold`). It checks once per start and on "Try again"; leaving the area later does not lock the app. Either permission (precise or approximate) is enough for the gate: 10 km is far larger than the approximate error. "Log in" is hidden until D-009.
4. **Report location: precise is required (Q4, Q7, review S1).** The form reads one fix when it opens and on "Refresh location"; Submit uses the stored fix and does not wait for GPS. It shows the reporter's own coordinates with 5 decimals. It needs `ACCESS_FINE_LOCATION`: with "Approximate" (Android 12+) the fix is about 2 km off and snapped to a grid, so unrelated reports in the same cell would get the same point and group. Without precise location the form shows its own message (`report_location_precise_needed`) and Try again offers the upgrade. `reportTicket` refuses (0, 0) and stores the fix in `tickets`, `ticketLocations` (exact) and `publicTickets` (rounded to 2 decimals by `toAnonymousView()`).
5. **10 m grouping.** Before creating a ticket, `FirestoreTicketsRepository.findMatch` queries `ticketLocations` with three equality filters (`categoryId`, `situation`, `active == true`; served by the automatic single-field indexes, no composite index) and runs the existing pure rule `TicketsList(...).findNearby` on the results (active, same category and situation, at most 10 m by Haversine, nearest wins). No try/catch around the query (the person's choice: offline it answers from the cache; school-project simplicity).
   - No match: the ticket is created as in F-011 (`ReportOutcome.CREATED`).
   - Match: `joinTicket` first reads the reporter's own tickets (the F-011 `participantIds` query). If the match is there, nothing is written (`ALREADY_FOLLOWING`; the creator never ends up in `followerIds`). Otherwise one batch writes `tickets/{id}/reports/{uid}` and `FieldValue.arrayUnion(uid)` on `followerIds` and `participantIds` (`JOINED`). `commit()` is not awaited, as in F-011.
   - `reportTicket` returns `ReportOutcome?` (`null` = refused) instead of the id; `MainActivity` shows one snackbar per outcome.
6. **Scope is ignored and the joiner's media stay in `reports/{uid}` (Q5).** Grouping uses only category, situation and 10 m (brief I.2 Obs.). The joiner's description **and** photos/videos are stored in their own `tickets/{id}/reports/{uid}` document (attachments PENDING, `uploadedById` = the joiner), never appended to the shared ticket. The shared ticket gains only the follower; its `attachments`, `publicTickets` and `stats/summary` do not change. So a PRIVATE reporter's photos can never appear on a PUBLIC ticket, which anonymous users see with its media (brief I.1.C). This is the authors' reading of a case the brief leaves open.
7. **`ticketLocations.active = isActive` (Q6).** `true` only for OPEN, INFO_REQUESTED and IN_PROGRESS, as `findNearby` and decision 0005 define "active". A report next to a RESOLVED ticket creates a new one.
8. **Map: Google Maps Compose 6.1.0, as Contacts_#3.** `ui/components/TicketMap(location, exact, modifier)` draws a `GoogleMap` with `rememberCameraPositionState { CameraPosition.fromLatLngZoom(...) }`.
   - Coarse (`exact = false`, anonymous detail, through `CoarseLocationMap`): zoom 14, a `Circle` of 750 m (primary colour, 25% fill), no `Marker`, and `MapUiSettings` with zoom controls, the map toolbar and every gesture off, so the map cannot be moved or zoomed in. 750 m because rounding to 2 decimals moves a point by up to about 700 m (review N3). No coordinates as text.
   - Exact (`exact = true`, for D-013): a `Marker` at zoom 15 and the default gestures.
   - Previews (`LocalInspectionMode`) draw a placeholder box.
9. **Maps API key in `AndroidManifest.xml`, as in class.** `<meta-data android:name="com.google.android.geo.API_KEY" ...>` inside `<application>`, committed and included in the ZIP. A placeholder value (`PASTE_MAPS_API_KEY_HERE`) is committed until the person pastes the real key. This overrides the CLAUDE.md "never commit secrets" rule for this one key, by the person's explicit choice. Recommended: limit the key in Google Cloud to the Maps SDK for Android (API restriction).

### Rejected
- **osmdroid** (the plan and decision 0012 Q6): no key, but it is not the class practical, it is a View library inside `AndroidView`, its repository was archived in Nov 2024, and it needs a User-Agent and a tile cache configuration. The person chose the class library.
- **The Maps key in `local.properties`** (the usual way): the ZIP excludes `local.properties`, so the grader's build would show a blank map.
- **A rationale panel before the request** (the plan, `.claude/rules/kotlin.md`): the class asks at start; the denied message explains afterwards.
- **Continuous location updates for the gate or the form** (Q2): one fix is enough; updates come with D-014.
- **Reading the centre from `municipality/main`** (Q1): the document does not exist, and reading it adds a listener, a missing-document case and an offline first-start case for a value that never changes.
- **Geohash or a latitude/longitude bounding box query:** a geohash needs a new field and hand code or a library; a bounding box needs range filters on two fields (a composite index). With only the active tickets of one category and situation the candidate list is small, so filtering in the app is enough.
- **Appending the joiner's media to the shared ticket** (decision 0002's first wording): would publish a PRIVATE reporter's photos on a PUBLIC ticket.
- **Appending them except PRIVATE-into-PUBLIC:** needs `scope` in `ticketLocations` and a second rule.
- **Grouping only reports with the same scope:** a condition the brief does not have, and two tickets for one problem.
- **`active` = "not CLOSED"** (decision 0010's first wording): a report could join a RESOLVED ticket, against `findNearby` and decision 0005.
- **A try/catch around the grouping query:** removed at Gate 1 by the person.

## Consequences
- **The grader sees the map only if the real key is in the ZIP.** The manifest must hold the real key, not the placeholder, when D-015 builds the ZIP. Without a valid key the map shows grey tiles (the app still works).
- **Do not add an Android-app (package + SHA-1) restriction to the key.** Google Cloud's Android restriction checks the signing certificate's SHA-1 together with the package. The grader builds from the ZIP with their own debug keystore, so a different SHA-1, and the map would be blank. Anyone with the ZIP can use the key; the API restriction and the billing budget alert (decision 0012) limit what that costs.
- Anonymous users never see exact coordinates: `publicTickets` stores 2 decimals (decision 0006) and the map shows a 750 m circle at a far zoom with gestures off.
- Users who grant only "Approximate" can use the app as anonymous users (the gate passes) but cannot submit a report until they allow precise location.
- Offline, the grouping query reads only the local cache, so a match against tickets this device has never loaded is missed and a second ticket is created (decision 0002 asked for "against cached data"). Two citizens reporting the same spot at the same time can also make two tickets (no transaction, decision 0010).
- Without the try/catch, a failing `get()` in `findMatch` or `joinTicket` (for example `PERMISSION_DENIED` once rules are deployed) would crash the app from `viewModelScope`. In test mode it does not happen.
- A rotation relaunches the start-up permission request (as in Contacts_#3); Android answers at once when already granted, and the gate does not re-check once INSIDE. If the user rotates while the first dialog is open, the gate can show DENIED for a moment (review N1, skipped by the person).
- Other followers and the creator do not see a joiner's description or media; only the joiner and operators can read `reports/{uid}`. F-013 must upload report media too; D-013 should show each ticket's reports to operators.
- D-013 and F-014 must keep `ticketLocations.active` in step with `isActive`: false on RESOLVED, true again on reopen, false on CLOSED.
- D-014 reuses `LocationRepository` and adds location updates and the background permission (the `ProximityService` pattern of Contacts_#3).
- F-016 adds `POST_NOTIFICATIONS` to the same start-up request.
- Device checks D1-D14 and D10b (01-coding-plan) and the S1 check (grant Approximate, open the form) have not run yet: no device, and no real key.
