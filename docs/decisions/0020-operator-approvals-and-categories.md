## Context
- **Brief I.3.D:** the operator views a pending citizen's registration (name, georeferencing, NIF) and activates it. **I.3.E:** the operator creates, activates, deactivates and edits the problem categories; citizens report only on active ones. (The PDF could not be opened in the planning session; the I.3.D fields come from the task file, plan R6. Check the PDF before the defence.)
- **Decision 0003:** a ticket stores `categoryId` plus a `categoryName` snapshot, so a category change must never rewrite tickets.
- **The session already reacts to `registrationStatus`.** `SessionViewModel` listens to `users/{uid}`; a change from PENDING to ACTIVE turns `PENDING_CITIZEN` into `CITIZEN`, and the redirect opens the dashboard with "+" (decision 0015). Activation needs no new code on the citizen's side.
- **The draft `firestore.rules` already allow what D-012 writes:** operators read and list `users`; the validation update `changedKeys().hasOnly(['registrationStatus', 'validatedBy', 'validatedAt'])` with `validatedBy == request.auth.uid` and `resource.data.role == 'CITIZEN'`; `categories: allow write: if isOperator()`. They are **not deployed** (decision 0012 Q5, amended 2026-11-13): the test-mode database accepts any write until 2026-12-10.
- Before D-012, `ApprovalsRoute` and `CategoriesRoute` were `PlaceholderScreen`s inside `RequireAccess(OPERATOR)`, categories were only read (`TicketsRepository.activeCategories()`, F-011) and written by `DebugSeed`, and a citizen could be activated only by a hand edit in the console.

## Decision
- **Pending list (Q4).** `UsersRepository.pendingCitizens(): Flow<List<Citizen>>` is a live query `users.whereEqualTo("registrationStatus", "PENDING").snapshots()`. One equality filter is enough: operators have no `registrationStatus`, and `toProfile()` drops anything that is not a citizen. The list is sorted by the document's `createdAt` in the app, oldest first (a queue), read leniently (`(get("createdAt") as? Number)?.toLong() ?: 0L`, review N2). No `orderBy`, so no composite index is needed.
- **Activation write (Q6).** `activateCitizen(citizenId, operatorId)` is one `update` of exactly the three keys of the draft rule: `registrationStatus: "ACTIVE"`, `validatedBy` (the operator's Auth uid, from the session) and `validatedAt` (epoch ms from the device clock, like every other time in the app). Not awaited, so it is queued offline; a refusal is only logged. Idempotent: a second activation rewrites the same three fields. `model/Citizen` gains no `validatedBy` (no screen shows it).
- **Activate only, with a confirmation (Q2, Q5).** The detail has one action, Activate, which opens an `AlertDialog` because the app has no undo. `activate()` runs only while the dialog is open and the citizen is PENDING, and closes the dialog and sets `activated` before it writes, so a fast double tap writes, shows the snackbar and goes back once (review S2). There is no Reject.
- **Detail fields (Q3).** Name (heading), NIF, e-mail, phone (hidden when blank), photo (when uploaded) and the georeferencing on the F-012 `TicketMap` with the exact marker; (0, 0) shows "Location not available". The contact data helps the operator check a doubtful registration; D-011 keeps `users/{uid}.email` in step with Auth for this.
- **A separate detail route and two ViewModels.** `PendingCitizenRoute(citizenId)` carries only the uid (like `TicketDetailRoute`). `PendingCitizensViewModel` (the list) and `CitizenApprovalViewModel` (one citizen, through the existing `observeUser`) are route-scoped and created inside `RequireAccess(OPERATOR)`, so their listeners end with their back-stack entries. This is the tickets' list -> detail pattern, which both authors already explain.
- **A separate `CategoriesRepository` (Q1).** New `CategoriesRepository` / `FirestoreCategoriesRepository` (Diogo's files): `allCategories()` (every category, active and inactive, live, sorted with `Collator`), `addCategory(name)` (`document().set(Category(name).toCategoryDocument())`, an auto-id, `active: true`), `renameCategory(id, name)` (`name` only) and `setActive(id, active)` (`active` only). It reuses F-011's `toCategory()`, `toCategoryDocument()` and `CATEGORIES`; only the `toCategoryDocument()` KDoc line in `FirestoreMapping.kt` changed. Writes are not awaited. The report form keeps reading `TicketsRepository.activeCategories()`, so Francisco's `ReportViewModel`, its factory and `TicketsRepository` are untouched; two readers of one collection share the cache.
- **Name rules, no delete (Q7, Q8).** Trimmed, not blank, at most 40 characters (`MAX_CATEGORY_NAME_LENGTH`), unique ignoring case among all categories (inactive ones too), checked in `CategoriesViewModel.onEditorSave` against the loaded list; Add is hidden and refused while the list is loading (review N1). Saving an unchanged name writes nothing. Names are not translated (municipality data). Deactivation is the safe "delete": tickets keep their `categoryId`.
- **Editing through an Edit icon button**, not a tap on the row (plan, review N4): the row holds two actions (Edit and the active switch, a `toggleable(role = Role.Switch)` area), and a separate button gives each a clear label for TalkBack.
- **No `SavedStateHandle` (Q9).** The editor dialog (id, typed name, error) and the confirm dialog live in the ViewModel state, so they survive rotation; they are lost on process death (short drafts).
- **No rules edit (Q10).** The existing drafts already restrict the three writes to operators. Nothing is deployed; no `firebase` command was run.
- **Top bar and gate (Q11, Q12).** The detail's title is "Registration" / "Registo" (`TopBarScreen.PENDING_CITIZEN`) with the normal operator menu. Pending citizens stay outside the 10 km gate (D-010 Gate Q12).

### Rejected
- **Reject and a `REJECTED` status:** the brief asks only to activate; a new enum value, session state and citizen screen for something not asked. A wrong registration stays pending; deleting it is a console task.
- **One `OperatorAdminViewModel`** for both screens (the task file's suggestion): it would hold two unrelated features and keep the categories listener alive on the approvals screen.
- **A list/detail two-pane with the selection in the ViewModel:** needs a `BackHandler` and makes Up behave differently per orientation; not worth it for a few fields.
- **Category writes in `TicketsRepository`:** Francisco's file, more coordination, no behaviour gain.
- **Deleting categories:** the brief lists create, activate, deactivate and edit; a delete would leave tickets pointing to a missing id.
- **`FieldValue.serverTimestamp()` for `validatedAt`:** it would be the only Timestamp in `users` and the only server time in the model's sense; every other time is client epoch ms (decision 0003).
- **A second filter `role == "CITIZEN"`:** adds nothing and is the only thing that could ask for a composite index.

## Consequences
- **Operator-only writes are enforced only by the app (R1).** Menu entries, `RequireAccess`, the ViewModels created inside the guard and a single write path (`FirestoreCategoriesRepository`, called only from `CategoriesViewModel`; `activateCitizen`, called only from `CitizenApprovalViewModel`). Because the rules are not deployed, any client with the project config can write `categories` or set its own `registrationStatus` against the test-mode database. The draft rules show the server design; say so at the defence.
- **The draft validation rule checks the keys, not the values (review N3, not edited).** An operator could set `registrationStatus` to any string or rewrite an ACTIVE citizen's `validatedAt`. Suggested terms, for both authors if the rules are ever deployed:
  ```
  && resource.data.registrationStatus == 'PENDING'
  && request.resource.data.registrationStatus == 'ACTIVE'
  && request.resource.data.validatedAt is int
  ```
  With them a second operator's activation is refused instead of "last write wins".
- **Duplicate names are possible (R5, review N1 residual).** The check is client-side. Offline with an empty cache, the first snapshot is an empty `fromCache` one, so the list "loads" empty and a name that exists on the server passes; two operators at once can also create the same name. Server-side uniqueness would need a `categoryNames` index document (as `nifs`) or a function.
- **A rename inside an open report form keeps the old name (R4).** `ReportViewModel` stores `categoryName` when the citizen picks the category; the listener refreshes the dropdown, but not the selected name, so a ticket submitted after a rename stores the old name. A deactivation is caught (`isValid` fails, "Choose a category."). Francisco's file; optional fix in `submit()`: take the name from the current `categories` list.
- **Old tickets keep the old name.** No ticket, `publicTickets` or `ticketLocations` document is touched by a rename or a deactivation (decision 0003, as intended).
- **A hand-edited user document can empty the pending list (review R2-N1, not fixed).** `toProfile()` (from D-009/D-011) reads typed fields strictly (`getString`, `getGeoPoint`, `getBoolean`, `getLong("photoUpdatedAt")`). A wrong-typed field in one `users` document throws inside `pendingCitizens()`, and its `.catch` emits an empty list and ends the listener: "No registrations are waiting." until the screen is reopened. The app itself always writes the right types. Fix: `runCatching { doc.toProfile() }` per document.
- **The confirm dialog can stay open after a concurrent activation (review R2-N2, not fixed).** If another operator activates the citizen while this operator's dialog is open, `canActivate` turns false but `confirming` stays true; Activate in the dialog then does nothing and only Cancel or a tap outside closes it. Rare (two operators, same citizen, same moment). Fix: close `confirming` in the listener when the citizen is no longer PENDING.
- **`.catch` ends the listeners.** As in the other repositories, a listener error emits an empty list once and the flow ends; the screen recovers when it is reopened.
- **Not verified (no device check run yet):** the approvals list (PENDING only, empty state, rotation); the detail fields and map; Activate -> confirm -> snackbar, the citizen leaving the list, and the console showing only the three fields; the two-device activation (the citizen's waiting screen turning into the dashboard with "+", and a report submitted); Activate offline; a fast double tap on Activate (S2); category add, rename and toggle in the list and the console; the validation errors; the report form dropping a deactivated category and showing a renamed one while old tickets keep their name; Add, Edit and rotation with each dialog open (S1, typed name kept); landscape on the three screens; citizens and anonymous users sent home from the three routes.
