## Context
- **Brief I.2.C:** the citizen may change their profile, except name, NIF and georeferencing. **I.3.C:** the operator may change their profile, except name and NIF. **I.2.A / I.2.F:** the citizen's impact-detection choice lives in the profile, and F-015 (Francisco) reads it.
- **MFA makes re-authentication two-step.** Every account has an SMS factor (decision 0015). For such a user `reauthenticate(EmailAuthProvider...)` throws `FirebaseAuthMultiFactorException`, as sign-in does, so a re-authentication is password + SMS code through the same resolver.
- **An e-mail change is out of band.** `verifyBeforeUpdateEmail(new)` only sends a link. The Auth e-mail changes when the user opens it, possibly on another device and much later. `users/{uid}.email` was written at registration, and the draft update rule forbade the owner from changing `email` at all.
- **The rules are drafts and not deployed** (decision 0012 Q5, amended 2026-11-13). The database is in test mode until 2026-12-10, so any client can write any field today.
- The registration form pieces were `private` in `RegisterScreen.kt` and took `RegisterUiState`.

## Decision
- **Editable set per role, and an allow-list in code.**
  - Read-only: name, NIF, role, the current e-mail and, for citizens, registration status and georeferencing (5 decimals, the user's own point). They use the Register text field with `readOnly = true` (no keyboard; TalkBack reads "read only").
  - Editable: phone (the D-010 rule), photo (gallery or camera), and impact detection for citizens.
  - `UsersRepository.updateProfile(user, ProfileChanges)` builds its map only from `phone` and, when `user is Citizen`, `impactDetection`. The photo goes through the worker. No path writes name, NIF, georeferencing, role, registration status or e-mail (the e-mail has its own path, below).
- **One Save, not awaited (Q6).** Save is enabled when something changed and gates on the phone rule. The Firestore `update()` is not awaited (as F-011): it is queued in the local cache, also offline, and the `users/{uid}` listener feeds `Session.SignedIn.user` at once. So the impact setting takes effect as soon as Save is pressed, offline too. A server refusal is only logged.
- **Re-authentication = current password + SMS code, through the D-009 resolver flow (Q2).** `AuthRepository.reauthenticate(password)` returns `SecondFactorRequired(challenge)` from the same private `challengeOf(e)` that `signIn` uses. The existing `sendSecondFactorCode` and `resolveSecondFactor` finish it. Then `changePassword(new)` (`updatePassword`) or `requestEmailChange(new)` (`verifyBeforeUpdateEmail`) runs at once.
- **Change e-mail and Change password are routes with one ViewModel (Q10).** `ChangeEmailRoute` and `ChangePasswordRoute` (guarded like `ProfileRoute`) share `CredentialChangeViewModel(change, isOperator, ...)` with the steps FORM -> CODE -> DONE, modelled on `LoginViewModel`. The challenge and the verification id stay in private fields, never saved. The passwords are never saved; after process death the form returns with only the new e-mail. Back is ignored while the change itself runs (review N1).
  - E-mail form, before Firebase is called: the D-010 e-mail rule, then "same as the current e-mail" (ignoring case), then for an operator the council domain (`municipality/main.emailDomain`, read as on Register).
  - A wrong current password gives an error on that field and sends no SMS.
- **The e-mail sync is owned by `SessionViewModel` (Q3).** In the signed-in branch of `flatMapLatest`, the **first** `Found` snapshot is compared with the Auth e-mail. If they differ, `users.syncEmail(uid, email)` writes one field, not awaited. A later snapshot in the same branch never triggers a write (review S1), so two devices cannot overwrite each other in a loop and a refused write is not retried in a loop. Profile also calls `reloadAccount()` once per visit (best effort), so a link opened elsewhere shows up.
- **The profile phone is contact data, separate from the SMS factor (Q1).** Changing it does not touch the MFA enrolment. A hint under the field says so. Changing the MFA phone is out of scope.
- **Unique photo work with `REPLACE` (Q8).** `ProfilePhotoUploader.enqueue` uses `enqueueUniqueWork("profile_photo_<uid>", REPLACE, ...)`, so two quick saves cannot finish in the wrong order.
- **Photo version `photoUpdatedAt` (review S2, the plan's R4 fallback).** `ProfilePhotoWorker` writes `photoPath` and `photoUpdatedAt` (client epoch ms) in one `update`. Profile uses `"<url>#<photoUpdatedAt>"` as the Coil memory and disk cache key, and clears "Uploading the new photo" when the version changes, not the URL. After Save the saved local file stays on screen until the upload ends.
- **Draft rules: an owner allow-list (Q4, slice 8 and `3b3dfb1`).** The owner's `users/{uid}` update is now `changedKeys().hasOnly(['phone', 'photoPath', 'photoUpdatedAt', 'impactDetection', 'email', 'fcmTokens'])`. `impactDetection` is allowed only when `role == 'CITIZEN'`. `email` may change only to `request.auth.token.email` with `email_verified`, and an operator's must stay in `municipality().emailDomain`. `fcmTokens` stays for F-016. **Not deployed**; no `firebase` command was run. The file is shared, so Francisco must be told.

### Rejected
- **An immediate impact switch** (written on toggle): a second write path next to Save (Q6).
- **Dialogs on the Profile screen** for e-mail and password: the `MultiFactorResolver` step and rotation are simpler in a route-scoped ViewModel (Q10).
- **Syncing the e-mail from `ProfileViewModel`:** it would never run if the user does not reopen Profile, and D-012 needs the current e-mail.
- **Checking on every snapshot** (the first slice 7 version): a stale second device wrote the old e-mail back, and a refused write retried without end (review S1).
- **A `pendingEmail` field in Firestore:** a second source of truth with nothing in Auth to compare it with.
- **Re-enrolling MFA when the phone changes:** two extra SMS flows, an unenrolment, a lockout risk, and not asked for by the brief (Q1).
- **Removing the stored photo (Q7):** it would also need a Storage delete. Only a photo picked in this visit can be discarded.
- **A two-pane landscape (Q11):** one centred column (`FormColumn`, at most 480dp), as Register.

## Consequences
- **Locked fields are protected only by the app** while the rules are not deployed. A direct write to name or NIF succeeds against the test-mode database. The "direct write is denied" check can only be shown in the draft (Rules Playground or emulator), never on the live database (R8).
- **The operator domain is checked by the client only for the Auth e-mail (R7).** Auth cannot enforce it without Cloud Functions, and `isOperator()` checks only `email_verified`. The draft rules refuse only the Firestore copy outside the domain.
- **Once per subscription, not once per account value (review R2-N1, accepted).** `session` uses `SharingStarted.WhileSubscribed(5_000)`. After more than 5 s in the background, collection restarts, `flatMapLatest` starts a new branch, and the check runs once more with the cached account; `retry()` does the same. A second device whose cached account is stale (its refresh token revoked by the link, its ID token still valid for up to about an hour) can therefore write the **old** e-mail once per return to the foreground, and once at a cold start, until its token is refused and it is signed out. It does not loop, and the next sign-in or reload on the up-to-date device writes the new e-mail again. The KDoc in `SessionViewModel` ("a second device with an old cached account cannot write the old e-mail back") over-claims; rewording it, or tracking the checked `AuthAccount` by identity in the ViewModel (review option b, four lines), is a follow-up. Not observed on a device (needs two devices).
- **The session ends after the e-mail link (R2, observed).** Opening the link revoked this device's session. The app stayed on the "link sent" screen and Profile still showed the old e-mail for the same visit (the reload had already run). Reopening Profile ran the reload, which hit the revoked token, and the session became Anonymous (the decision 0015 involuntary path) with **no message**. The user then logs in with the new e-mail and the sync runs. A short "Your e-mail changed; sign in with the new address" notice is a follow-up (device-check nit).
- **The session survives the MFA re-authentication (R1, observed).** After the password change, "Back to profile" returned to Profile, still signed in; the route-scoped ViewModel was not lost.
- **"E-mail already in use" is hidden at request time (R3, observed).** With e-mail enumeration protection `verifyBeforeUpdateEmail` succeeded for an address that belongs to another account, and the app showed the "link sent" message. The clash can only show when the link is opened; the user stays on the old e-mail. The `EMAIL_IN_USE` branch stays for projects without the protection.
- **The photo cache key works (R4, observed).** After a second photo the new image showed, not the cached old one. Whether the overwrite kept the same download URL was not recorded; the version key makes the answer irrelevant.
- **Two photos before the first upload ends (review R2-N3).** Save A, then save B while A uploads: `REPLACE` cancels A's worker. If A's worker had already written, its snapshot clears the pending notice and the saved preview, so for a moment the screen shows A with no notice until B's snapshot shows B. Harmless and rare.
- **Orphan file on REPLACE (R5).** A cancelled worker does not delete its source file in `filesDir/images`. Rare, accepted.
- **A revert link may unenrol MFA (R6, from the Firebase docs; not observed).** Opening "revert e-mail change" from the old inbox restores the old e-mail and may remove the second factor. The session then shows Account setup, and the sync makes Firestore follow.
- **Password change signs out other devices** at their next token refresh (an involuntary sign-out, decision 0015).
- **If the worker gives up**, the "Uploading" notice stays for the visit and the saved local file it deleted no longer draws (no retry UI, as D-010).
- **`currentEmail` is read once (review N6, not fixed).** `CredentialChangeViewModel` takes `auth.account.value?.email` in its constructor. If the account changes while the screen is open, the read-only field and the "same e-mail" rule use the old value. Fix: collect `auth.account` in `init`, as `ProfileViewModel` does.
- **The draft rules do not type-check the allow-listed fields (review N5, R2-N2; not edited).** The owner could write `phone: "abc"`, `impactDetection: "yes"`, any `photoPath` or a string `photoUpdatedAt`. The typed getters (`getBoolean`, `getLong`) would then throw while mapping, which harms only the owner. Suggested terms for the owner update rule (both authors; Francisco to be told):
  ```
  && (!changedKeys().hasAny(['phone']) || request.resource.data.phone.matches('^[29][0-9]{8}$'))
  && (!changedKeys().hasAny(['impactDetection']) || request.resource.data.impactDetection is bool)
  && (!changedKeys().hasAny(['photoPath']) || request.resource.data.photoPath is string)
  && (!changedKeys().hasAny(['photoUpdatedAt']) || request.resource.data.photoUpdatedAt is int)
  ```
  (Review N5 wrote `^[0-9]{9}$`; `^[29][0-9]{8}$` is the app's own `isPortuguesePhone` rule.)
- **F-015 contract.** The detector runs only while `session.accessRole == AccessRole.CITIZEN && ((session as? Session.SignedIn)?.user as? Citizen)?.impactDetection == true`, keyed on that Boolean, so Save on Profile unregisters it at once. Pending citizens may change the switch, but `accessRole` is not `CITIZEN` for them, so the detector does not run.
- **Not verified:** the console values (`phone`, `impactDetection: false`, `photoPath` + `photoUpdatedAt`, `users/{uid}.email` after the change); Register with a photo after the worker change; the two-device e-mail case; the old password refused at login; the draft rules in the Rules Playground; F-015's detector stopping (F-015 does not exist).
